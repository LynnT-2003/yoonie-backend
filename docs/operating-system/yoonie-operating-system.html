1 Introduction

1.1 Overview

Yoonie runs a hotel from booking to checkout. A guest books on the hotel's own site; Yoonie plans the work that booking creates; staff are dispatched on their phones and report each step from where the work happens; the desk watches it live on the web and answers only when something goes wrong. Every step is a structured, timestamped event, ready for analytics and AI.

Part A describes each flow: an overview with its sequence diagram, the endpoints the web and app call, and each endpoint's request and response. Part B is the reference: data schemas, roles, decisions, open items, build status and source documents. The rules every flow follows are in docs/OPERATING_RULES.md; this document shows how they run.

2 Guest Booking

2.1 Overview

The guest picks dates and a room, adds extras, and checks out. Yoonie holds the capacity for 15 minutes, creates the order as confirmed with payment at the hotel, and hands it to the planner.

sequenceDiagram
    actor G as Guest
    participant W as Booking site
    participant API as Yoonie API
    participant DB as Inventory slots
    participant PL as Planner
    G->>W: Dates, room, extras
    W->>API: GET /rooms, /services, /inventory/availability
    API-->>W: Catalogue, rooms left
    G->>W: Check out
    W->>API: POST /inventory/hold (stays, services)
    API->>DB: held += qty if held + booked + qty <= capacity
    API-->>W: holdId, expiresAt (15 min)
    W->>API: POST /orders (guest, lines, holdId, attribution)
    API->>DB: held to booked
    Note over API: Order CONFIRMED · payment UNPAID · PAY_AT_HOTEL
    API->>PL: plan order
    PL-->>API: room turnaround, pickup, tour fill check
    API-->>W: order, orderToken
    W-->>G: Booking confirmed, pay at hotel

3 Dispatch Planning

3.1 Overview

Every booking becomes work. The planner turns order lines into tasks with an owner, a deadline and a natural key, so planning twice never creates a duplicate. Loading today's Dispatch also tops up room work for every room that isn't ready.

sequenceDiagram
    participant API as Yoonie API
    participant PL as Planner
    participant T as Tasks
    actor D as Driver (app)
    actor Desk as Desk (web)
    API->>PL: order confirmed / flight edited
    PL->>T: upsert hk:{room} on check-in date (ready by ETA + 60 min)
    PL->>T: upsert pickup:{order}:{line} on landing date (van's default driver)
    PL->>D: PICKUP_READY card (new, or time changed)
    PL->>T: tour:{slot}: raise or clear fill check
    Desk->>API: GET /dispatch?serviceDate=today
    API->>T: ensure every non-ready room has today's task
    API-->>Desk: tasks + cleaning status + assignee names

4 Room Turnaround

4.1 Overview

A room is inspected and ready before its guest walks in. Housekeepers take rooms from the open pool on their phones; the room and its task always move together; the supervisor inspects standing in the room.

sequenceDiagram
    actor HK as Housekeeper (app)
    participant API as Yoonie API
    actor Sup as Supervisor (app / web)
    actor Desk as Desk (web)
    actor Drv as Driver (app)
    Note over API: Checkout or booking: room DIRTY, task in open pool
    HK->>API: GET /staff/me/tasks
    API-->>HK: my rooms + open pool, by arrival
    HK->>API: POST /staff/rooms/{id}/transition IN_PROGRESS
    Note over API: claims the room for this housekeeper
    API-->>Desk: board: Cleaning · Noi
    opt Guest already on the way
        Drv->>API: pickup step GUEST_ON_BOARD
        API->>HK: CRITICAL: guest arrives ~15:45
    end
    HK->>API: transition CLEAN
    API->>Sup: Room 305 ready for inspection
    alt Pass
        Sup->>API: transition INSPECTED
        API->>HK: Room 305 passed inspection
    else Fail
        Sup->>API: transition DIRTY + reason
        API->>HK: CRITICAL: Reclean room 305
    end

10.1 Overview

Staff sign in once; the app opens the screen for their job. Every action works offline: it is applied on screen straight away, queued on the phone, and replayed when the signal comes back.

    participant API as Yoonie API
    S->>App: email + password

    S->>App: tap a step (no signal)
    App->>Q: queue with Idempotency-Key

    Q->>API: replay in order
    alt 2xx
        API-->>Q: done
    else 409

    else other error
        Q->>Q: retry, drop after 3 attempts
    end

15 Decisions

#DecisionSource
1The worker reports work from where it happens; screens observe. Desk entries are recorded as on the worker's behalf.Operating rules L1
2One write path per fact: rooms move only through POST /staff/rooms/{id}/transition, which moves the room and its task together.Operating rules L2
3Housekeeping is an open pool: starting a room claims it; managers can assign.Product, 25 Oct
4ACKNOWLEDGED is retired. Ownership comes from the assignee; pickups have a real Accept step; tours have a recorded decision.Product, 25 Oct
5Airport pickup is a driver-reported journey with problems the desk must answer (Keep waiting / No-show).Product, 25 Oct
6Tour fill: dispatcher decides Keep or Merge; Cancel needs a manager.Product, 25 Oct
7Guest checkout confirms immediately as pay at hotel; payments are recorded at the desk.Code
8Room ready-by = ETA + 60 min; ETA is the flight landing, else check-in time. Guest on board tightens it to now + 45 min.Code
9Notifications are stored then delivered by the worker; responses return who was notified.Operating rules L4
10Steps only move forward; repeats are no-ops; staff mutations take an Idempotency-Key.Operating rules L6
11Humans decide anything that costs money or touches a guest; AI may only recommend until a rule is approved.Operating rules L8
12Guest tour and ops tour are separate; the ops tour only runs after login.Product, 25 Oct
